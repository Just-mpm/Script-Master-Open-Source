### [SUGGESTION] JSDoc de `appDrawerPaperSx` desatualizado — falta MobileBottomNav

- **Arquivo:** `src/theme/surfaces.ts:43-51`
- **Confidence:** 95/100
- **Categoria:** Documentation
- **Problema:** O JSDoc de `appDrawerPaperSx` lista apenas `PublicHeader` e `GuestMobileNav` como consumidores, omitindo `MobileBottomNav` que também o importa e usa.
- **Evidência:**

```ts
// src/theme/surfaces.ts:43-51
/**
 * Estilo glass compartilhado para o `Paper` de Drawers laterais de navegação
 * (mobile hamburguer do `PublicHeader` e do `GuestMobileNav`).
 * ...
```

```ts
// src/components/app/MobileBottomNav.tsx:56
import { appDrawerPaperSx, glassSurfaceSx } from '../../theme/surfaces';
// src/components/app/MobileBottomNav.tsx:342
sx: { ...appDrawerPaperSx, width: 280 },
```

Grep confirmou exatamente 3 consumidores: `MobileBottomNav.tsx`, `GuestMobileNav.tsx`, `PublicHeader.tsx`.

- **Impacto:** Documentação enganosa — um desenvolvedor que ler apenas o JSDoc vai tentar refatorar `appDrawerPaperSx` achando que só 2 componentes dependem dele.
- **Sugestão:** Atualizar o JSDoc para listar os 3 consumidores ou usar uma descrição genérica ("Drawers laterais de navegação — MobileBottomNav, GuestMobileNav, PublicHeader").

### [SUGGESTION] JSDoc de `exportDotPulseKeyframes` referencia `mergeSx()` inexistente

- **Arquivo:** `src/theme/animations.ts:18`
- **Confidence:** 90/100
- **Categoria:** Documentation
- **Problema:** O exemplo de uso no JSDoc mostra `mergeSx(...)` que não existe no projeto (src ou tests). O padrão real é array syntax (`sx={[exportDotPulseKeyframes, {...}]}`).
- **Evidência:**

```ts
// src/theme/animations.ts:17-19
 * Uso:
 * ```tsx
 * <Box sx={mergeSx({ animation: 'exportDotPulse 1.6s ease-in-out infinite' }, exportDotPulseKeyframes)} />
 * ```
```

Grep confirmou que `mergeSx` não existe em nenhum arquivo `.ts`/`.tsx` em `src/` ou `tests/`. Os consumidores reais (`SidebarNavItem.tsx:173`, `MobileBottomNav.tsx:285`) usam array syntax.

- **Impacto:** Desenvolvedor que tentar copiar o JSDoc vai encontrar um erro de compilação (`mergeSx is not defined`). A documentação do JSDoc não reflete o uso real do símbolo.
- **Sugestão:** Atualizar o exemplo para usar array syntax, que é o padrão real do projeto e a recomendação oficial do MUI v9:

```tsx
 * <Box sx={[exportDotPulseKeyframes, { animation: 'exportDotPulse 1.6s ease-in-out infinite' }]} />
```

### [SUGGESTION] Escape hatch `SpeedPaintControls` mocka `glassPanelSx` com tipo incorreto (objeto vs função)

- **Arquivo:** `tests/video-render/SpeedPaintControls.unit.test.tsx:8-12`
- **Confidence:** 80/100
- **Categoria:** Testing
- **Problema:** O mock inline de `surfaces` em `SpeedPaintControls.unit.test.tsx` define `glassPanelSx` como um objeto vazio `{}`, enquanto a exportação real de `surfaces.ts` é uma função `(theme: Theme) => SystemStyleObject<Theme>`. O factory centralizado (`surfacesMock.ts`) usa `(): Record<string, unknown> => ({})` — tipo correto.
- **Evidência:**

```ts
// Mock atual (escape hatch):
vi.mock('../../src/theme/surfaces', () => ({
  insetPanelSx: () => ({ p: 2 }),
  glassPanelSx: {},     // ← OBJETO, não função
  appDrawerPaperSx: {},
}));

// Factory centralizado (correto):
export const surfacesMock = {
  glassPanelSx: (): Record<string, unknown> => ({}),  // ← FUNÇÃO
  ...
};
```

O componente `SpeedPaintControls` não chama `glassPanelSx()` atualmente (grep confirmou que `glassPanelSx` não é usado em `src/features/video-render/components/`), então o teste passa. Mas se o componente for refatorado futuramente para usar `glassPanelSx(theme)`, o teste quebrará silenciosamente com `TypeError: glassPanelSx is not a function`.

- **Impacto:** Risco latente de falso-positivo (teste passa mas mock não corresponde ao tipo real). A descoberta seria em produção ou em desenvolvimento, não silenciosa — mas o custo de debug seria maior do que corrigir o mock hoje.
- **Sugestão:** Alinhar o mock de `glassPanelSx` ao factory centralizado, usando uma função:

```ts
vi.mock('../../src/theme/surfaces', async () => {
  const { surfacesMock } = await import('../../__mocks__/surfacesMock');
  return {
    ...surfacesMock,
    insetPanelSx: () => ({ p: 2 }),  // override do que precisa ser específico
  };
});
```

Ou, se prefere manter inline, usar `glassPanelSx: () => ({})`.

## 4. O que parece saudável

- **Factory mock centralizado (`surfacesMock.ts`):** Padrão correto de import dinâmico dentro do factory do `vi.mock`, conforme documentação oficial do Vitest 4. JSDoc explica claramente o hoisting e por que não é uma função factory. Cobre todos os 5 exports de `surfaces.ts`.

- **Mocks migrados (3 amostras):** Usam corretamente `async () => await import(...)` com `surfacesMock`. Sintaxe idêntica ao padrão estabelecido em `tokensMock.ts`.

- **`MobileBottomNav.tsx`:** Zero `useCallback`. Comentário (linhas 122-125) referencia corretamente React 19, confirmando que `useEvent` não existe. Funções simples, sem memo desnecessário. 7 handlers removidos conforme planejado.

- **Array syntax do MUI v9:** `SidebarNavItem.tsx` e `MobileBottomNav.tsx` usam `sx={[exportDotPulseKeyframes, {...}]}` — padrão oficial confirmado pelo NotebookLM. Spread evitado corretamente para SxProps.

- **`appDrawerPaperSx` + spread em slotProps:** O spread em `MobileBottomNav.tsx:342` (`sx: { ...appDrawerPaperSx, width: 280 }`) é seguro porque `appDrawerPaperSx` é um objeto literal constante (nunca será callback function). Documentado em AGENTS.md como padrão de extensão.

- **`vitest.config.ts`:** Configurações documentadas com JSDoc. `pool: 'forks'`, `testTimeout: 15000`, `hookTimeout: 20000`, `maxWorkers: '50%'` — resolve 4 flakies pré-existentes. Sintaxe compatível com Vitest 4.

- **`CLAUDE.md`:** Espelho perfeito de `AGENTS.md` — diff vazio comprovado.

- **Testes de acessibilidade:** Presentes nos 3 testes de amostra (role, aria-label, aria-current, aria-expanded, tabIndex).

- **Escape hatches (4 de 5):** `assistantUi`, `ConfiguracoesPage`, `CaptionEditorPanel`, `VideoExportPanel` — todos usam tipos de mock corretos (funções mockadas como funções, objetos como objetos), justificados por precisarem de valores de retorno específicos.
