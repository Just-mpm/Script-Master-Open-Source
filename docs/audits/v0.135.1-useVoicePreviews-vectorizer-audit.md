## 3. Achados priorizados

### WARNING

### [WARNING] `VetorialBatchSceneWrapper` usa `useVideoConfig().durationInFrames` (duração TOTAL do batch) em vez da duração da cena — batch vetorial multi-cena desenha fração da animação por cena

- **Arquivo:** `src/features/speed-paint/store/speedPaintRenderController.tsx:227-246` (em especial linha 236)
- **Confidence:** 90/100
- **Categoria:** Bug (latente) | Architecture
- **Problema:** Dentro de uma `<Sequence>`, `useVideoConfig().durationInFrames` retorna a duração da composição raiz (o total do batch), enquanto `useCurrentFrame()` retorna o frame local da cena. O `WhiteboardScene` interpola `frame` local contra a duração total → cada cena do batch só desenha `sceneDurationInFrames/total` da animação e nunca atinge o hold.
- **Evidência:**
  - `Sequence.js` (remotion 4.0.448) provê apenas `SequenceContext` (offset de frame) e `use-video-config.js` lê o `VideoConfigContext` da composição raiz — o valor de `durationInFrames` não muda dentro da Sequence.
  - `speedPaintRenderController.tsx:236`: `const { durationInFrames } = useVideoConfig();` → passado em `WhiteboardScene` (linha 240).
  - `WhiteboardScene.tsx:242-252`: `interpolate(frame, [0, durationInFrames - 1], [0, totalDrawingLength], ...)` — `frame` é local (0..`sceneDurationInFrames`-1).
  - Ex: batch de 3 cenas de 15s @30fps → composição de 1290 frames; a cena 0 (frames locais 0..449) só desenha ~35% dos paths.
- **Gatilho:** latente hoje — `SpeedPaintPage.tsx:325` chama `startBatchRender` sem `renderMode`, então o lote é sempre mask e o branch `isVetorial` nunca roda. O contrato do escopo prevê o wrapper, portanto o bug dispara assim que o batch vetorial for habilitado pela UI.
- **Observação:** o comentário do código (linhas 168-171) afirma que "WhiteboardScene não aceita `sceneDurationInFrames` arbitrário" — isso é factualmente incorreto: `WhiteboardSceneProps.durationInFrames: number` aceita qualquer valor (o single render já passa a duração da composição).
- **Impacto:** vídeo de exportação batch vetorial com desenho incompleto por cena (e transição abrupta — WhiteboardScene não tem fade no overlap de 1s das Sequences).
- **Sugestão:** passar `sceneDurationInFrames` diretamente para `WhiteboardScene` no wrapper (a prop existe); eliminar a dependência de `useVideoConfig()` no wrapper. Se a intenção for animar a cena na duração total da cena (comportamento esperado), a correção é trivial.

### [WARNING] `sampleColors` mapeia cor por índice entre `bezierPaths` e `contours` — dessincroniza quando `fitBezierPaths` descarta contornos

- **Arquivo:** `src/features/speed-paint/lib/vectorizer.ts:808-830` (consumo em 1021-1029) + `src/features/speed-paint/lib/bezierFitting.ts:569-575`
- **Confidence:** 88/100
- **Categoria:** Bug (edge case) | TypeScript
- **Problema:** `fitBezierPaths` descarta contornos que falham (`processContour` → `null`, contador `dropped`), então `bezierPaths[i]` não corresponde a `contours[i]`. `sampleColors` usa `bezierPaths.map((_, i) => contours[i])` — a partir do primeiro descarte, todo path subsequente recebe a cor do contour errado.
- **Evidência:**
  - `bezierFitting.ts:569-575`: `if (path === null) { dropped += 1; continue; } out.push(path);`
  - `vectorizer.ts:814-828`: `bezierPaths.map((_, i) => { const contour = contours[i]; ... sampleColors no primeiro ponto do contour }`
- **Impacto:** paths com cores trocadas no resultado vetorial quando há contornos degenerados (ex.: path que falha no `buildValidatedPath`). Erro visual, sem crash — o pipeline continua, mas a imagem final pode ter cores incorretas em parte dos traços.
- **Sugestão:** retornar a associação contour→path de `fitBezierPaths` (ex.: índice do contour de origem junto com o `BezierPath`) ou passar `contourIndex` no resultado, eliminando o pareamento posicional.

### SUGGESTION

### [SUGGESTION] Import de `vetorialWorker.ts` na main thread executa `self.onmessage = ...` no `window` (efeito colateral global)

- **Arquivo:** `src/features/speed-paint/lib/imageProcessing.ts:6` + `src/features/speed-paint/lib/vetorialWorker.ts:89`
- **Confidence:** 92/100
- **Categoria:** Architecture
- **Problema:** `imageProcessing.ts` importa `supportsVetorialWorker` (runtime) de `./vetorialWorker`, que é o mesmo arquivo usado como worker. No contexto da main thread, `self` é `window` e o módulo sobrescreve `window.onmessage` globalmente ao ser avaliado.
- **Evidência:** grep confirma que nenhum código do app usa `window.onmessage` hoje — o handler injetado só retorna cedo (`msg.type !== 'process'`), então o impacto atual é nulo; o risco é latente (conflito com código futuro/terceiros e inclusão do módulo do worker no bundle principal).
- **Sugestão:** mover `supportsVetorialWorker()` para um módulo próprio (ex.: `vetorialWorkerSupport.ts`) ou reimplementar a checagem inline em `imageProcessing.ts`, removendo o import runtime do arquivo do worker.

### [SUGGESTION] Silenciar `MediaError.code = 4` também silencia 404s reais do asset de preview — diagnóstico perdido em produção

- **Arquivo:** `src/hooks/useVoicePreviews.ts:108-113`
- **Confidence:** 82/100
- **Categoria:** UX | Bug (diagnóstico)
- **Problema:** em vários navegadores, asset ausente (404) também resulta em `MEDIA_ERR_SRC_NOT_SUPPORTED` (code 4). Com o contrato atual (4 → `log.debug`), um preview removido/renomeado em `public/voice-previews/` vira silêncio total em produção (o logger suprime `debug`).
- **Evidência:** contrato implementado na linha 111 (`code === null || code === 0 || code === 1 || code === 4` → debug); trade-off documentado no próprio código, mas o caso "asset realmente não existe" fica indistinguível do falso positivo.
- **Sugestão:** em `log.debug`, incluir `networkState`/`error.message` (já incluído) e considerar um `log.warn` de baixa frequência para code 4 com `networkState === NETWORK_NO_SOURCE`, ou validar o asset via `fetch(HEAD)` antes de tocar — preservando o silêncio do falso positivo e mantendo diagnóstico de manutenção.

## 4. O que parece saudável

- **`useVoicePreviews`:** cleanup do unmount segue o padrão recomendado (token incremental + zerar `onerror`/`onended` + `pause` + remoção de `src` antes do `load()`) — validado contra o notebook React. Contrato de `MediaError.code` (0/1/4 → debug; 2/3 → error + `errorId`) implementado exatamente como especificado, com double protection (listener null + token) contra o falso positivo do Android.
- **`vectorizer.ts`:** `enrichPaths` valida `SVG_PATH_DATA_REGEX` antes de `getLength` (contrato cumprido); `applyVetorialSafetyLimits` cobre os 3 invariantes (sanitização numérica, 500 paths, 250 KB de `d`) com logs `warn` descritivos e determinismo preservado; regex compilada uma vez; `sortPaths` determinístico (sem `Math.random`).
- **`imageProcessing.ts`:** try/catch no `new Worker({type:'module'})` com fallback para main thread (contrato cumprido — cobre Safari < 15 / CSP restritivo); clonagem do `ImageData` para o worker; `settled` guard em `resolveOnce`/`rejectOnce` evita settle duplo; abort listener limpo em todos os caminhos.
- **`speedPaintRenderController.tsx`:** discriminação `'paths' in animation` sem cast mentiroso; single render vetorial usa `useVideoConfig()` corretamente (fora de Sequence); `currentRenderId` + `abortController` em escopo de módulo protegem renders obsoletos; batch reutiliza o mesmo componente/composição com key estável.
- **Testes:** 8/8 do hook cobrem o contrato de codes; `vectorizer.safetyLimits` cobre os 4 invariantes do limitador de forma determinística via `__testing`; e2e valida 500 paths + 250 KB + retrocompatibilidade do mask.
