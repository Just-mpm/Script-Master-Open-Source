### [WARNING] Caminho de `vi.mock` corrompido em 2 testes migrados

- **Arquivos:**
  - `tests/components/ActionBar.features.test.tsx:57`
  - `tests/components/public/PublicHeader.component.test.tsx:27`
- **Confidence:** 99/100
- **Categoria:** Bug
- **Problema:** A string do primeiro argumento de `vi.mock` contém uma aspa simples extra no início (`"'../../src/theme/surfaces'"` em vez de `'../../src/theme/surfaces'`). O módulo mockado efetivamente não existe — o mock nunca é aplicado.
- **Evidência:**

```typescript
// ActionBar.features.test.tsx — linha 57
vi.mock("'../../src/theme/surfaces'", async () => {  // ← " extra no início
  const { surfacesMock } = await import('../__mocks__/surfacesMock');
  return surfacesMock;
});

// PublicHeader.component.test.tsx — linha 27
vi.mock("'../../../src/theme/surfaces'", async () => {  // ← " extra no início
  const { surfacesMock } = await import('../../__mocks__/surfacesMock');
  return surfacesMock;
});
```

O valor da string é `'../../src/theme/surfaces'` (com aspas simples literais). O módulo real que deveria ser mockado é `../../src/theme/surfaces` (sem aspas). O Vitest não resolve o caminho corrompido, então o mock nunca substitui o módulo real.

**Contraste com a forma correta** (exemplo do `surfacesMock.ts` JSDoc):

```typescript
vi.mock('../../src/theme/surfaces', async () => {   // ← sem aspas extras
  const { surfacesMock } = await import('../../__mocks__/surfacesMock');
  return surfacesMock;
});
```

- **Impacto:** Os mocks são **dead code** — o módulo `surfaces` real é carregado nos testes em vez do mock. Atualmente isso é inofensivo porque `surfaces.ts` não tem efeitos colaterais na inicialização (só define funções e objetos). Porém:
  1. Se `surfaces.ts` ganhar **qualquer efeito colateral** (ex: acesso a `window`, chamada de API, import de imagem), o teste quebrará em runtime.
  2. Se o comportamento do `surfaces` real diferir do mock (ex: uma função real que lança exceção em JSDOM), o teste passará falso positivo.
  3. Mantenedores podem se confundir ao ver o mock importado mas não ativo.
- **Sugestão:** Remover a aspa simples extra no início do path. O padrão correto é:

```typescript
vi.mock('../../src/theme/surfaces', async () => {
  const { surfacesMock } = await import('../__mocks__/surfacesMock');
  return surfacesMock;
});
```

### [SUGGESTION] JSDoc de `exportDotPulseKeyframes` mostra padrão `mergeSx` que não é usado no código real

- **Arquivo:** `src/theme/animations.ts:18-19`
- **Confidence:** 95/100
- **Categoria:** Documentação
- **Problema:** O exemplo de uso no JSDoc referencia uma função `mergeSx` que parece não existir no projeto, enquanto todos os consumidores usam o padrão array syntax (`sx={[keyframes, {...}]}`) que é o idiomático do MUI v9.
- **Evidência:**

**JSDoc (stale):**
```typescript
/**
 * Uso:
 * ```tsx
 * <Box sx={mergeSx({ animation: 'exportDotPulse 1.6s ease-in-out infinite' }, exportDotPulseKeyframes)} />
 * ```
 */
```

**Uso real nos 2 consumidores (`MobileBottomNav.tsx:284-301` e `SidebarNavItem.tsx:172-189`):**
```tsx
sx={[
  exportDotPulseKeyframes,
  {
    // props específicas do componente
    animation: videoIsRendering
      ? 'exportDotPulse 1.6s ease-in-out infinite'
      : 'none',
    // ...
  },
]}
```

- **Impacto:** Desenvolvedores que consultarem o JSDoc podem tentar usar `mergeSx`, que não existe, ou podem ficar confusos sobre qual padrão seguir. O array syntax é o padrão correto e documentado no AGENTS.md.
- **Sugestão:** Atualizar o JSDoc para refletir o array syntax real:

```typescript
/**
 * Uso:
 * ```tsx
 * <Box sx={[exportDotPulseKeyframes, { animation: 'exportDotPulse 1.6s ease-in-out infinite' }]} />
 * ```
 */
```

### [SUGGESTION] Mock de `ConfiguracoesPage` tem 2 exports faltando em relação ao módulo real

- **Arquivo:** `tests/pages/ConfiguracoesPage.component.test.tsx:66-70`
- **Confidence:** 90/100
- **Categoria:** Manutenibilidade
- **Problema:** O mock inline de `surfaces` só cobre 3 dos 5 exports (`glassPanelSx`, `insetPanelSx`, `appDrawerPaperSx`). Faltam `glassSurfaceSx` e `searchFieldSx`. Embora o componente testado não importe esses exports (confirmado por leitura do `Configuracoes.tsx`), a diferença aumenta o custo de manutenção quando `surfaces.ts` for modificado.
- **Evidência:**

```typescript
// Mock atual — 3/5 exports
vi.mock('../../src/theme/surfaces', () => ({
  glassPanelSx: () => ({ p: 2, borderRadius: 3 }),
  insetPanelSx: () => ({ p: 2 }),
  appDrawerPaperSx: {},
}));
```

**Real em `surfaces.ts` — 5 exports:** `glassPanelSx`, `insetPanelSx`, `glassSurfaceSx`, `appDrawerPaperSx`, `searchFieldSx`.

- **Impacto:** Se no futuro `ConfiguracoesPage` (ou um componente filho intermediário) passar a importar `glassSurfaceSx` ou `searchFieldSx`, o mock não terá esses exports, causando erro em runtime (`undefined is not a function`). O `surfacesMock` factory (usado pelos 33 testes migrados) já cobre todos os 5 exports.
- **Sugestão:** Migrar este teste para usar o `surfacesMock` factory, ou adicionar os exports faltantes ao mock inline:

```typescript
vi.mock('../../src/theme/surfaces', () => ({
  glassPanelSx: () => ({ p: 2, borderRadius: 3 }),
  insetPanelSx: () => ({ p: 2 }),
  glassSurfaceSx: () => ({}),           // ← adicionar
  appDrawerPaperSx: {},
  searchFieldSx: {},                     // ← adicionar
}));
```

**Nota:** O arquivo `tests/__mocks__/surfacesMock.ts` existe justamente para evitar esse tipo de drift. Se o mock customizado inline é necessário (escape hatch documentado), pelo menos os exports existentes no módulo real devem ser cobertos para evitar falsos negativos futuros.

## O que parece saudável

- **`src/theme/animations.ts`** — implementação limpa e bem comentada. `as const satisfies SxProps<Theme>` é o padrão TypeScript correto para extrair tipos literais mantendo compatibilidade com o tipo esperado. Consumidores usam array syntax do MUI v9 (`sx={[keyframes, {...}]}`), que é o padrão recomendado.
- **`src/theme/surfaces.ts`** — `appDrawerPaperSx` como `SxProps<Theme>` (objeto, não função) está correto para o uso como spread (`{ ...appDrawerPaperSx, width: 280 }`). JSDdoc mapeia precisamente os 3 consumidores (confirmado via supergrep: `MobileBottomNav`, `GuestMobileNav`, `PublicHeader`).
- **`MobileBottomNav.tsx`** — handlers todos como funções simples (sem `useCallback`), consistente com a recomendação do React 19 para componentes sem `memo`. Uso de `useStore` com seletor (duas slices isoladas) evita re-renders desnecessários. Comentário na linha 122-125 documenta a decisão de design corretamente.
- **`SidebarNavItem.tsx`** — `overflow` condicional (`visible` vs `hidden`) baseado em `showExportDot` resolve corretamente o clip do dot sem afetar o `::before` da borda ativa (que vive dentro do item, não do overflow edge). Uso de array syntax com `exportDotPulseKeyframes` replicado de forma consistente entre os dois estados (colapsado/expandido).
- **`tests/__mocks__/surfacesMock.ts`** — factory bem estruturado e documentado. Acerta o padrão de import dinâmico dentro do factory do `vi.mock` para contornar o hoisting do Vitest 4. Tipagem `Record<string, unknown>` nos retornos é pragmaticamente correta para mocks. Cobre os 5 exports de `surfaces.ts`.
- **`vitest.config.ts`** — configurações documentadas com comentários que explicam o porquê de cada setting (`pool: 'forks'`, `testTimeout: 15000`, `hookTimeout: 20000`, `maxWorkers: '50%'`). A sintaxe do Vitest 4 está correta (`maxWorkers` em vez do antigo `maxForks`/`maxThreads`).
- **`package.json`** — versão `0.134.0` consistente com o changelog do `AGENTS.md`. Dependências alinhadas com a stack documentada. Sem discrepâncias.
- **Testes não migrados** (`ConfiguracoesPage`, `assistantUi`) — ambos documentados como "escape hatches" com mocks customizados. O padrão é consistente com a política do projeto: factory para casos genéricos, mock inline para testes que precisam de valores específicos.
